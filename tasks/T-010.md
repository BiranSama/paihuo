## 目标

界面能通过已有的本机 WebSocket 连接，完成第 1 期私聊需要的全部操作：看成员、开私聊、
翻历史、发消息、实时看到回复和工作记录、看工作项。

做完之后，T-011 的界面只需要调用这些命令、订阅这些事件，不碰任何业务规则。

## 要做的事

1. 在 `packages/shared/src/api.ts` 定义第 1 期的命令和事件类型，覆盖 `docs/interfaces.md` 第 2.1、2.2 节，其中：
   - 第 1 期实现：`member.list`、`conversation.open`、`message.page`、`message.send`、`work.list`、`work.get`、`system.info`
   - 只定义类型、先返回"尚未实现"：`member.create`、`member.update`、`member.archive`（T-012）、`session.sleep`、`session.wake`（T-009）、`request.answer`（T-013）
2. 每条命令都校验参数，不合法的返回明确的错误码，不断开连接。现有"格式错误就关闭连接"的行为只保留给无法解析的消息。
3. 命令按 `id` 回结果；事件主动推送给所有已连接的界面。
4. `message.send` 立即回"已收到"和消息 ID，处理过程通过事件推送。
5. `message.page` 按 `seq` 向前或向后取一页，单页有上限（默认 50）。
6. 单条消息上限从 16 KB 调整到能容纳一页消息的大小，并说明取值理由；推送给界面的单个事件也有上限，超出时截断并标注。
7. 写一个不依赖界面的测试客户端，用它跑通"列出成员 → 打开私聊 → 发消息 → 收到回复事件 → 翻页"的完整流程（大脑用假适配器）。
8. 更新 `docs/interfaces.md` 第 2 节与实际实现不一致的地方：写在 PR 里，由组长或网页端 Claude 同步文档。

| 验收 | 实测证据 |
| --- | --- |
| 1. 私聊主流程 | 测试客户端依次列成员、开私聊、发送中文和 emoji、收回复、取历史。发送方先收到带消息 ID 的回执，再收到事件。另用打包后的内核子进程验证实际入口、数据目录及关闭后重新开库。 |
| 2. 非法请求 | 对错误方向或页长、无效游标、超长正文、未知方法及非法封包返回结构化错误。同一 socket 随后成功列成员。无法解析的 JSON 和二进制帧收到 1008，超大入站帧收到 1009。 |
| 3. 预留命令 | 六个预留方法均用合法参数验证 NOT_IMPLEMENTED，用不完整参数验证 INVALID_PARAMS；确认名册未改变。 |
| 4. 多界面 | 两个独立 WebSocket 收到相同消息 ID 与成员终稿。握手期间的事件和待审批请求在首个成功回包后按序补发；过慢客户端的积压有界。 |
| 5. 鉴权 | T-001 的六个服务测试继续通过，覆盖缺失令牌、错误令牌、无协议与不可信 Origin 的升级拒绝。 |
| 6. 分页 | 真实 SQLite 预置一万条。最新页只查 51 行，返回 50 条并用额外一行判定后页；正反向游标正确。额外用大正文、转义和多字节文本遍历历史，两向均能逐条取齐。 |
