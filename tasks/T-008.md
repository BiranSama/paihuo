## 目标

内核里有一个调度模块：老板发给某位成员的私聊消息，能找到或新建这位成员的私聊会话，
排队、投递给适配器、把事件和回复写进存储；成员可以把一件事转成任务会话独立运行，
同一位成员的多条会话可以并行。

本卡做完，派活的"大脑"还是假的，但除了真实 harness 以外，私聊的主干都通了。

## 要做的事

1. **适配器注册表**：按 `RuntimeKind` 取得适配器。测试里注册假适配器。
2. **会话解析**：给定成员和场合（种类 + 场合 ID），找到未归档的会话；没有就调用适配器 `start` 并写入 `sessions`。前言由一个可注入的"前言提供者"生成，本卡给一个默认实现：成员名字、职责、对老板的称呼，加上 ADR-0007 里"何时开口"的几条规则。成员目录里的人设和记忆文件由 T-012 接入。
3. **每会话队列**：同一条会话同一时刻只有一轮在跑；新消息进队列，`runs` 记为 `queued`，按到达顺序执行。不同会话互不阻塞。
4. **一轮的执行**：新建 `runs` 记录，调用 `send`，消费事件流：
   - `text_delta` 只转发，不落库；
   - `message_done` 写成一条成员消息；
   - `tool_started`、`tool_finished`、`error` 各写一行摘要进 `run_events`，不存完整内容（C-04）；
   - `needs_approval` 写进 `run_events` 并通过事件通知上层，本卡不代答，策略等 Q-014；
   - `turn_done` 按原因把 `runs` 结束为 `done`、`cancelled` 或 `failed`。
5. **事件出口**：调度模块对外发出 `docs/interfaces.md` 第 2.2 节列出的那些事件（`message.created`、`message.delta`、`run.started`、`run.ended`、`run.event`、`member.status`、`work.updated`），用一个简单的订阅接口。T-010 会把它接到 WebSocket。
6. **任务会话**：提供"开始一项工作"的函数：新建 `work_items` 和它的目录，为负责人新建 `kind = 'task'` 的会话，`cwd` 指向工作目录，投递第一条消息。提供"结束一项工作"：状态改为 `done`。产物登记不在本卡（Q-011）。
7. **并行上限**：同时处于运行中的会话数有上限（可配置，默认 4）。超出的等前面结束再开始，界面能看到它在排队。同一成员的私聊会话不计入上限，保证私聊总能回话。
8. **成员状态**：根据该成员各会话的情况算出"空闲 / 工作中"，变化时发 `member.status`。"休眠"由 T-009 补。
9. **启动恢复**：内核启动时，存储层已把未结束的 `runs` 标为 `unknown`；本卡把对应会话的队列清空并发一条系统消息"上次的工作被中断，状态待核对"，不自动重做。

## 验收标准

每条都用假适配器的自动化测试验证。

- [x] 第一次给某成员发私聊，会新建一条私聊会话；第二次复用同一条。
- [x] 同一会话连发三条消息，三轮按顺序执行，任何时刻只有一轮在跑。
- [x] 两位成员同时收到消息，两边并行执行，互不等待。
- [x] 同一位成员的私聊会话在跑时，它的任务会话也能同时跑，两边的事件和消息不串。
- [x] 成员的任务会话在跑时，私聊发消息能立刻开始处理（不排在任务后面）。
- [x] 运行中会话数达到上限后，新的任务会话排队，前一个结束后自动开始。
- [x] `run_events` 里只有一行摘要；存储里找不到完整的工具输出。
- [x] 假适配器在一轮中途抛错，`runs` 记为 `failed`，会话仍可接下一条消息。
- [x] 假适配器发出 `needs_approval`，事件被记录并通知出去，这一轮不会被自动放行。
- [x] 启动时存在 `unknown` 的运行，会出现一条"状态待核对"的系统消息，不会自动重跑。
- [x] 一万条消息的对话里发新消息，内存中不会读入全部历史。验证：测试加代码审阅。
